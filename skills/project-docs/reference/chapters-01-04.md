# 01–04 各篇模板

这四篇让新人建立认知：项目长什么样、为什么这样、代码从哪读。

写作要求（贴代码前先读文件、引用带 `path:line`、篇幅、用词）见 SKILL.md 的 Phase 3，下面不再重复。不同类型项目怎么调整见 [project-types.md](project-types.md)。

---

## 01 架构

**要解决的问题**：让读者知道项目"长什么样"。

**素材**：`.project-map.md` 的第 1、2、3、6 节。

```markdown
> 这篇面向刚接触项目的新同学，从"这是什么"开始，先建立整体印象。

## 0. 开始之前
读者可能不知道的基础概念：
- 这类项目是干什么用的（配一个生活里的例子）
- 关键词是什么意思（从术语表搬过来）
- 为什么用这门语言、这个框架，而不是更流行的那个

## 1. 分几层
ASCII 分层图：每层是什么，依赖朝下。宽度别超 80 字符。

## 2. 目录里都是什么
带注释的目录树，每个目录一句话。
排除 node_modules / build / vendor 这些。

## 3. 各模块细说（从底层往上）
每个模块：
- 能做什么
- 里面几个主要的类是什么关系 —— 用 Mermaid classDiagram 或 flowchart
- 真实用法示例（先 Read 再贴，带路径行号）

## 4. 怎么构建的
构建文件之间什么关系，几个关键编译或打包选项什么意思。
细节留给 06，这里只给个全貌。

## 5. 示例工程是怎么组织的
如果有 demo / example，讲讲它的整体结构。
这是 .project-map.md 第 5 节那条流程的宏观视角。

## 6. 想找某段代码去哪
| 想知道什么 | 看哪 |
|---|---|
| X 是在哪初始化的 | `path:line` 的 `funcName()` |
```

**容易做错**：把 `tree` 的输出直接贴上来不加注释。没有注释的目录树对新人几乎没价值。

## 02 设计思想

**要解决的问题**：让读者知道"为什么这么设计"。

**素材**：`.project-map.md` 第 6 节 + 读代码时的观察 + README/CONTRIBUTING 里作者自己的说法。

```markdown
> 这篇解释项目里每个重要设计决定是出于什么考虑。

## 1. 总体思路（一句话）

## 设计 N：<名称>
（每一条都按下面三段写）

**问题**：不这么设计会遇到什么麻烦？
要写具体场景，别写"不够灵活""难以维护"这种空话。
❌ 「不用抽象接口就不够灵活」
✅ 「新增一种传输方式要同时改 5 个文件，每处都得加一个 if 分支」

**做法**：项目怎么解决的？给代码或 Mermaid 图。

**好处和代价**：解决了什么，**付出了什么**。
代价必须写。只讲好处就成软文了，新人读完不知道边界在哪。

## 汇总
| 设计 | 体现在哪（类 / 文件 / 机制）| 解决什么 | 代价 |
```

**关键**：这些要从代码里读出来，不是套一遍通用设计模式清单。如果只写得出"用了工厂模式""符合单一职责"，说明还没读懂——回去继续读代码。

## 03 语言特性

**要解决的问题**：读代码前的语言准备。**只讲项目里真正出现的。**

**素材**：`.project-map.md` 第 4 节 + 写的时候精读入口文件。

```markdown
> 这篇只讲本项目代码里出现的语言特性，都结合真实代码说。

## <特性名>
（每个都按下面写）

**项目里哪用了**：真实代码 + `path:line`
**能省什么事**：对比"没这个特性得怎么写"
**要记住的**：1–3 条，不要写成语言教程

## 命名习惯速查
| 什么东西 | 怎么起名 | 例子（来自真实代码）|
```

**按语言挑，通常需要讲的**：

| 语言 | 一般要讲 |
|---|---|
| C++ | 纯虚接口、多重继承、`std::bind`/lambda、`override`、`= delete`、初始化列表、RAII、智能指针 |
| Rust | 所有权和借用、trait、`Result`/`?`、生命周期标注、`Arc<Mutex<T>>` |
| Java / Kotlin | interface 默认方法、泛型擦除、注解、协程、`companion object`、`data class` |
| Go | interface 隐式实现、goroutine 和 channel、`defer`、错误处理习惯、struct 嵌入 |
| Python | decorator、`dataclass`、ABC、`asyncio`、上下文管理器、类型注解 |
| TypeScript | `interface` 和 `type` 的区别、泛型约束、装饰器、联合类型和窄化、工具类型 |
| React / Vue | Hooks 的规则、Composition API、响应式怎么实现的、props 和 slot |

**挑选标准**：不讲这个，新人读第 04 篇会不会卡住？会卡就写，不会就删。别写成语言手册。

## 04 代码导读

**要解决的问题**：从入口跟着代码走一遍，把前面讲的概念和具体代码对上。

**素材**：`.project-map.md` 第 5 节那条完整流程，就是这篇的主线。

```markdown
> 这篇从入口出发，一步步跟着代码，直到一个完整流程跑完。

## 0. 整体流程图
Mermaid flowchart：涉及哪些模块，数据往哪走。
先给图再进细节，不然读者看三段就迷路了。

## 1. 入口文件逐段讲
贴代码，每段加注释。注释要说"为什么这么写"，不是把代码翻译成中文。
❌ `// 创建一个 Manager 对象`
✅ `// Manager 必须在 Bus 之前构造，因为它持有 Bus 的注册回调`

## 2. 主要类型 A（提供方 / 服务端）
- 结构：为什么这样继承或组合
- 构造函数：初始化了什么，顺序有什么讲究
- 主要方法：逐段注释

## 3. 主要类型 B（使用方 / 客户端）
同上

## 4. 一次完整流程，一步一步看
把 .project-map.md 第 5 节展开：编号步骤 + Mermaid sequenceDiagram，
追一条数据从发出到被处理完的全过程，每步标出 `path:line`。

## 5. 代码里的命名习惯
| 什么东西 | 怎么起名 | 例子 |

## 6. 加一个新模块要写哪些文件
文件列表 + 每个文件干什么。
具体怎么写留给 07，这里只让读者知道大概是个什么形状。
```

**容易做错**：贴大段代码不裁剪。一次贴 80 行会把重点埋掉——挑关键的 10–20 行，其余用 `// ...` 省掉，注明完整代码在 `path:line`。
